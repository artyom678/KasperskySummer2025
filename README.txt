Пререквизиты:
1) ОС Linux
2) компилятор, поддерживающий C++20
3) CMake версии 3.28.3 и новее

Сборка:
1) перейти в папку с проектом
2) mkdir build && cd build
3) cmake ..
4) cmake --build .

В директории build появятся поддиректории Client, ProcessingServer, DisplayServer.
Эти директории содержат исполняемые файлы client, processing_server, display_server соответственно.

Использование:
Первым следует запустить сервер отображения: ./display_server <port>
Далее следует запустить сервер обработки: ./processing_server <port> <display_ip> <display_port>
Затем клиентскую часть : ./client <proc_serv_ip> <proc_serv_port>

Пояснения:

Для того, чтобы реализовать это решение, потребовалось написать свой EventLoop (чтобы асинхронно обрабатывать клиентов)
и совместимые с ним обёртки над POSIX-сокетами (смотрите eventloop.hpp и socket.hpp соответственно). EventLoop основан
на epoll, отсюда и требование ОС Linux.

За построение и парсинг http запросов и ответов отвечает класс HttpProcessor.

Для работы с форматом JSON используется header-only библиотека nlohmann/json.

Классы ResponseAccumulator и RequestAccumulator - вспомогательные классы, которые служат главным образом для накопления больших
запросов/ответов (которые мы не можем прочиать за 1 раз).

Класс StringValidator отвечает за валидацию данных, которые прислал пользователь (в качестве валидации я решил сделать
проверку, что все отдельные строки (данные) состоят только из букв и цифр. Если валидация прошла успешно, клиент получает
http ответ 200 ОК, если же валидация не пройдена, то клиент получит ответ 400 Bad Request.

Если данные прошли валидацию, то мы приступаем к их обработке - за это отвечает класс String Processor. Он принимает на вход
вектор строк и конкатенирует их через пробел, отбрасывая дубликаты.

Клиент асинхронно читает данные из стандартного потока (для этого реализован класс StreamDescriptor из socket.hpp) в цикле,
когда пользователь вводит пустую строку, то данные упаковываются в JSON, формируется HTTP POST запрос, и данные отправляются
на сервер. Клиент может снова вводить данные.

Сервер обработки обрабатывает клиентов асинхронно и устроен так, что у нас есть несколько потоков (здесь это std::thread::hardware_concurrency()), в каждом из которых
есть свой EventLoop и Acceptor (смотрите в socket.hpp). Все Acceptor'ы слушают один и тот же порт засчёт установки флага SO_REUSEPORT.
Какой-то из Acceptor'ов принимает клиента, далее этот клиент будет целиком обрабатываться в этом же потоке. Для связи с сервером отображения каждый рабочий
поток имеет свой сокет. Для обеспечения последовательной отправки обработанных пользовательских запросов этому серверу служит класс StringSender.

Сервер отображения асинхронно принимает запросы сервера обработки, парсит их и выводит на стандартный поток вывода.

Для обработки аргументов командной строки используются соответствующие *Config классы.
